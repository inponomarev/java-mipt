Java и Android

  • При разработке Android, Google использовали Java как язык, javac, стандартные API, байткод, но не виртуальную машину и не реализацию API.

Синтаксис тот же, типизация строже

int i = 2;
if (i = 4) {
    printf("head\n");
} else {
    printf("tail\n");

Напечатает head (i = 4 — выражение, равное 4, воспринимаемое как «истина»).

int i = 2;
if (i = 4) {
    println("head");
} else {
    println("tail");
}

Не скомпилируется (как и в C, i = 4 — выражение, возвращающее 4, но его тип не boolean).

Синтаксис тот же, безопасности больше

int array[2];
printf("%d\n", array[5]);

Неопределенное поведение (включая чтение чужих данных или segmentation fault).

int[] array = new int[2];
println(array[5]);

ArrayIndexOutOfBoundsException, который можно перехватить и обработать. Цена: проверка при каждом обращении к элементу массива!

Синтаксис (почти) тот же, безопасности больше

Employee* e = NULL;
printf("%d\n", e->salary);

Неопределенное поведение (включая аварийное завершение программы).

Employee e = null;
println(e.salary);

NullPointerException, который можно перехватить и обработать.

Проблема несовместимости платформ

  • На разных типах компьютеров разные

    • Endianness…​

    • Размер регистров и ссылок (sizeof(int), sizeof(void *)…​

    • Floating point hardware & format…​

  • Приходилось разрабатывать разные версии программ для разных платформ (или писать спагетти из #ifdef)

JVM

  • Java bytecode — исполняемый код виртуальной машины. Виртуальные машины (написанные на C++) написаны для разных платформ, все они исполняют байт-код.

  • LLVM intermediate representation — схожая идея, появившаяся позднее.

  • Решается вопрос не только кроссплатформенности, но и безопасности.

Путь байткода: верификация, интерпретация и JIT-компиляция

  • Перед выполнением байткода, JVM выполняет его статическую проверку (https://docs.oracle.com/javase/specs/jvms/se25/html/jvms-4.html#jvms-4.10)

  • Если код невалидный (например, stack underflow) — VerifyError

Путь байткода: верификация, интерпретация и JIT-компиляция

  • JVM начинает исполнение с интерпретации байт-кода, накапливая статистику выполнения.

Путь байткода: верификация, интерпретация и JIT-компиляция

  • По мере того, как накапливается статистика использования кода, код компилируется в оптимизированный машинный код с использованием допущений, накопленных по статистике выполнения.

  • Скомпилированный код хранится в Code Cache (специальном сегменте оперативной памяти).

Путь байткода: верификация, интерпретация и JIT-компиляция

  • Если путь выполнения меняется, срабатывает "uncommon trap" и выполнение возвращается к интерпретатору.

В низкоуровневых языках (например, C) мы контролируем аллокацию данных в памяти

typedef struct {
    int year;
    int month;
    int day;
} Date;
/* "stack allocation" */
Date val_date =
  {.year = 2026, .month = 8, .day = 15};
/* "heap allocation" */
Date* ptr_date = malloc(sizeof(Date));

*ptr_date = val_date; // values copied
ptr_date->day++; // value on heap increased
print_date(val_date); // 2026-8-15
print_date(*ptr_date); // 2026-8-16

В C мы контролируем передачу данных по ссылке или по значению

Date modify_months(Date date1, Date *date2) {
  date1.month++;
  date2->month++;
  return date1;
}

Date result =
  modify_months(
    *ptr_date, // value at pointer
    &val_date  // address of value
);

print_date(val_date); // 2026-9-15
print_date(*ptr_date); // 2026-8-16
print_date(result); //2026-9-16

  Date dateTo = (Date){.year = 2026,
    .month = 8, .day = 16};

Java: свобода и производительность в обмен на безопасность

  • Нет больше * и &, всё определено за нас.

  • «Объекты» и «примитивы/value-объекты» ведут себя по-разному.

@AllArgsConstructor @ToString
class Date {
  int day; int month; int year; }

int modifyMonths(int month, Date date) {
  month++; date.month++;
  return month; }

Date d = new Date(15, 8, 2026);
int month = 8;
int result = modifyMonths(month, d);
println(month);  // 8
println(d);      // Date(d=15, m=9, y=2026)
println(result); // 9

Массивы объектов в Java (не value-объектов) — всегда массивы ссылок

Date[] dates = new Date[3];

dates[0] = new Date(1, 1, 2023);
dates[1] = new Date(2, 2, 2024);
dates[2] = dates[1];

Потерянная ссылка — не проблема

dates = new Date[0];

Обоснование решений из 1995-го года

  • Нет (явных) аллокаций на стеке

  • Нет ручной деаллокации

⇒ нет проблемы «висячих» ссылок

  • Garbage collection

⇒ нет проблемы «потерянных» ссылок

  • 8 предопределенных примитивных типов (byte, short, int, long, char, float, double, boolean), не являющихся частью иерархии типов объектов.

Компромисс ради быстродействия при отсутствии лучшего решения. Осложнил систему типов, обучение языку Java, привёл к дальнейшим проблемам типа использования типов-обёрток в generics.

Виртуальная машина

  • Достоинства

    • WORA

    • Safety/техническая безопасность: исключение фатальных сбоев на сервере

    • Security/информационная безопасность: защита от злонамеренных действия

  • Недостатки

    • Overhead по производительности и памяти

    • Отсутствие гибкости, предоставляемой низкоуровневыми языками

Garbage Collection

  • Разработчику не нужно заботиться о высвобождении памяти

  • Ссылок на объект нет? — garbage collection

  • Достоинства:

    • Меньше кода

    • Не бывает некорректных ссылок (на разрушенный объект)

    • Меньше утечек памяти

  • Недостатки:

    • Не контролируем время работы GC

    • STW-паузы (бывает, в неподходящий момент)

Типы коллекторов в современной Java

GC полностью изолирован от исполняемого кода.
Семантика не меняется при замене одного GC на другой!

  • Serial (for single-threaded, small heaps)

  • Parallel (high throughput, potentially 10..100ms or more STW)

  • G1 (Garbage First — default one since Java 9, generational, balanced on medium-to-large heaps, 200ms is default soft target)

  • ZGC: latency over throughput (normally <1ms)

  • Shenandoah latency over throughput (normally <1ms)

  • Epsilon (no GC at all)
