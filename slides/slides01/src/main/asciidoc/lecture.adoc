== Java и Android

* При разработке Android, Google использовали Java как язык, `javac`, стандартные API, байткод, но не виртуальную машину и не реализацию API.
* 11 лет судов Google с Oracle (2010--2021), пока решение не было вынесено в пользу Google.
* Kotlin (язык, компилирующийся в тот же JVM байт-код) провозглашён основным языком Android.
* Oracle не признаёт настоящей «Джавой» то, что работает на Android.
* https://www.businessofapps.com/data/android-statistics/[По некоторым оценкам], в мире около 3.9 млрд Android-устройств.

== Проблема несовместимости платформ

* На разных типах компьютеров разные
** Endianness...
** Размер регистров и ссылок (`sizeof(int)`, `sizeof(void *)`...
** Floating point hardware & format...
* Приходилось разрабатывать разные версии программ для разных платформ (или писать спагетти из `#ifdef`)



== JVM

* Java bytecode -- исполняемый код _виртуальной машины_. Виртуальные машины (написанные на C++) написаны для разных платформ, все они исполняют байт-код.
* LLVM intermediate representation -- схожая идея, появившаяся позднее.
* Решается вопрос не только _кроссплатформенности_, но и _безопасности_.

== В низкоуровневых языках (например, C) мы контролируем аллокацию данных в памяти

[cols="50a,50a"]
|===
|
[source,c]
----
typedef struct {
    int year;
    int month;
    int day;
} Date;
/* "stack allocation" */
Date val_date =
  {.year = 2026, .month = 8, .day = 15};
/* "heap allocation" */
Date* ptr_date = malloc(sizeof(Date));

*ptr_date = val_date; // values copied
ptr_date->day++; // value on heap increased
print_date(val_date); // 2026-8-15
print_date(*ptr_date); // 2026-8-16
----

== Обоснование решений из 1995-го года

[cols="50a,50a"]
|===
|
* Нет (явных) аллокаций на стеке
* Нет ручной деаллокации
|  => нет проблемы «висячих» ссылок
|
* Garbage collection
|=> нет проблемы «потерянных» ссылок
|
* 8 предопределенных примитивных типов (`byte`, `short`, `int`, `long`, `char`, `float`, `double`, `boolean`), не являющихся частью иерархии типов объектов.
| Компромисс ради быстродействия при отсутствии лучшего решения. Осложнил систему типов, обучение языку Java, привёл к дальнейшим проблемам типа использования типов-обёрток в generics.
|===

== Конечно, подход Java к безопасности -- +++<br/>+++не единственный возможный подход...

[cols="20a,80a"]
|===
|
image::c_sharp_logo_2023.svg[{image-80-width}]

C#: «соперник Java», на 4 года моложе Джавы

* имеет GC, но также имеет `struct` для типов-значений, аллоцируемых «на стеке», и  `ref` для передачи данных по ссылке.
* контроль «утечек» `ref` производится компилятором: нельзя передать `ref` на локальную переменную туда, где ссылка сохранится после выхода из функции, создавшей локальную переменную.
* `List<int>` не использует типы-обёртки.

== Garbage Collection

[%step]
* Разработчику не нужно заботиться о высвобождении памяти
* Ссылок на объект нет? -- garbage collection
* Достоинства:
** Меньше кода 
** Не бывает некорректных ссылок (на разрушенный объект)
** Меньше утечек памяти
* Недостатки:
** Не контролируем время работы GC
** STW-паузы (бывает, в неподходящий момент)
